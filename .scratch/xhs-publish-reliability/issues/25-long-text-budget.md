# 25 — 长文本平台的打字预算口径

Status: resolved
Type: grilling
Blocked by: 10
Assignee: wayfinder-session (opencode)

## Question

10 定了「全量逐字、**无时间上限**」（选项 C），小红书安全（1000 字 ≈2.3min），但它同时定了 humanize 是全平台共享能力。长文本平台在 C 下会**必然**失败：

| 平台 | 单次输入上限 | 逐字耗时（均值 136ms/字） | 结果 |
|---|---|---|---|
| TikTok 配文 | 2200 字符（`docs/CLI.md:634`，代码明确） | ≈5.0min | 可能挤掉其它步骤 |
| YouTube 描述 | 5000 字符（**仅推断**） | ≈11.3min | 挤爆 15min 预算 |
| 知乎 / 公众号类长文 | 数千至上万字符 | ≫15min | **每次必然 `exit 1`（点击前超时）** |

需要决定：

1. **口径**：延长这些平台的发布预算（`PublishTimeoutBudget(timeout_seconds=...)` 平台级默认表）？接受必然失败？还是对长文平台**推翻 C**、改回「超限部分粘贴」？C 是用户裁定，本票不得默认推翻，必须显式确认。
2. **预算表**：若延长，按平台还是按「输入字符数 × 均值 + 固定余量」动态推导？`PublishTimeoutBudget` 当前只在构造时传秒数，是否需要新增工厂函数（不改变其契约）。
3. **失败语义**：预算耗尽仍发生在点击前 → `exit 1`（可无条件重跑）。但「重跑必然还是超时」意味着调度器会陷入确定性失败循环——`exit 1` 是否还够用，还是需要新的可操作信号（如 `exit 2` 用法错误：请求本身超出平台可承受的预算）。
4. **与 18 的关系**：18 管主动节奏与熔断；确定性超时会持续触发失败冷却，是否需要在 18 里为「配置性失败」开豁免（不计入熔断）。
5. **与 15 的关系**：15 的迁移顺序里，每个平台的「文本上界」必须先算出并写入迁移验收，否则迁移后该平台直接不可用。

## Comments

- 来源：10 的 HITL 决议（2026-11-11，选项 C「不设上限、全量逐字」）暴露出的跨平台后果。小红书不受影响，故不在 10 内解决。

## Answer

**决议（2026-11-11，HITL 逐题裁定）**

1. **口径 = 按长度分级（对 C 的显式修订）**：`len(text) ≤ 1000` → 逐字（10 原语义不变）；`> 1000` → **整段一次性写入**。C 的「不做超限降级」在**短文本上继续成立**，只对超过打字视野的长文本引入一次降级。理由：真人写 4000 字配文也是粘贴，而 4000 字逐字要 9.1min、Facebook 无上界时更是 2.4h——「逐字到底」在长文本上本身就是可测的脚本特征。
2. **阈值 = 1000 字，单例常量**：`HumanizeProfile.type_horizon_chars: int = 1000`，与其它参数同表；**平台不得复制第二份、不得按平台覆盖**（10 §2 / 15 的单例约束）。计数口径 = Python `len()` 码点（不是 11 的 UTF-16 加权，那条只用于平台标题上限）。
3. **超限写入机制 = `keyboard.insert_text(text)` 一次派发**：
   - **不用**剪贴板 paste（`navigator.clipboard.write` 失败时 `Ctrl+V` 会粘进用户上一条剪贴板内容 → **静默发错正文**；托管模式下短文本字段的剪贴板权限无实测证据）；
   - **不用** `fill()`（10 已禁）；
   - `insert_text` **不引入新事件签名**：10 §1 已定中文/emoji 只能逐字 `insert_text`，整条打字路径本来就是 insertText 事件；TikTok 配文现状就是它（`main_chrome.py:2428`），迁移前后零行为变化。
   - 粘贴后仍走一次 `after_type` 停顿（与逐字路径同形），不新增回读（11 的薄口径不变；`insert_text` 失败是硬异常 → 点击前 `exit 1`）。
4. **分支位置 = `Humanizer.type_text` 内部自动分流**：平台调用点完全不变，平台侧零知识；每次分流打一条 `info` 命中日志（`type_text→bulk insert_text, chars=NNN`），与 05 的命中日志同形，便于 dry-run 取证与将来调参。
5. **预算、退出码、18 全部不动**：
   - 15 分钟总预算保持常数；**不新增平台预算表、不新增工厂函数、不新增 `timeout_seconds` 推导**（打字成本被结构性封顶在 `1000 × 136ms ≈ 2.3min`）；
   - 25 原问题 3 的「新退出码 `2`」**取消**：不存在「确定性超时」这一类失败；
   - 18 不需要为「配置性失败」开熔断豁免（无此类失败）；码表沿用 0/1/9/10/11。
6. **事实更正（本票原前提）**：

| 票里写的 | 事实 | 置信度 |
|---|---|---|
| TikTok 配文 2200 | `TIKTOK_MAX_DESCRIPTION_LENGTH = 4000`（`tk_uploader/tk_config.py:25`）；2200 是 Instagram（`docs/CLI.md:634`） | 代码明确 |
| YouTube 描述 5000 会逐字 | 描述**故意用 `fill()`**：逐字输入 `#` 会触发话题补全并卡死发布流程（`youtube_uploader/main.py:238-252`）→ 不进打字路径 | 代码明确 |
| 知乎/大鱼长文逐字 | 正文是 **HTML 剪贴板粘贴**（`zhihu:105-120`、`dayu:133-144`、`xueqiu:97-102`）→ 正文永不进打字路径 | 代码明确 |
| 长文平台必然超时 | 修正后逐字路径只剩纯文本字段，成本被 1000 字上限钉住 | 代码明确 |

### 迁移后的字段分类（15 的逐平台上界表由此清单替代）

| 平台 / 字段 | 平台上限 | 迁移后路径 | 最坏逐字成本 |
|---|---|---|---|
| 小红书 标题 / 正文 | 20（UTF-16 加权）/ 1000 | 逐字 | 2.7s / **≈2.3min** |
| TikTok 标题（图文）/ 描述 | 90 / 4000 | 逐字 / ≤1000 逐字、>1000 bulk | 12s / ≈2.3min |
| Instagram 标题 / 配文 | 90 / 2200 | 逐字 / 通常 bulk | 12s / ≈0 |
| Facebook / facebook_page 配文 | 代码无上限（平台约 63k） | bulk | ≈0 |
| 抖音 / 快手 / 视频号 / 百家号 / 支付宝 标题+简介 | 代码未设上限（**仅推断** ≤1000） | 逐字 | ≤2.3min |
| 微博 / 虎扑 / 知乎视频 标题（+简介） | 30 / 40 / 50（简介 300） | 逐字 | ≤41s |
| 大鱼 / 知乎 / 雪球 **文章标题** | ≤100 | 逐字 | ≤14s |
| 大鱼 / 知乎 / 雪球 **文章正文** | 数千–2 万字 | **保持 HTML 剪贴板粘贴（不在本票范围）** | ≈0 |
| YouTube 标题 / 描述 | 100 / 5000 | **保持 `_fill_editable` 的 `fill()`**（`#` 补全约束） | ≈0 |

### 派生结论（对其它票）

- **15 解阻**：步 10（大鱼/知乎/雪球）前置由「先算出各平台文本上界 × 136ms 与预算表」改为「标题逐字 + 正文保持现有粘贴」；逐平台上界表**不再需要**，只保留上表的「字段 → 路径」分类。
- **15 的静态断言要开口子**：`fill(` 计数 = 0 这条**必须豁免 YouTube 的 `_fill_editable`**（标题与描述都走它），否则迁移路线与断言自相矛盾。豁免必须以「唯一 helper + 注释写明 `#` 补全原因」的形式落进 16 的断言。
- **文章正文粘贴不与长配文 `insert_text` 统一**：前者是为了保留富文本结构（必须），后者是行为降级（可选）；两者机制不同、不得合并成一个 helper。

### 测试断言（交 16）

1. `type_text("a" * 1000)` → 1000 次按键分派 + 1000 次 `Keystroke` 采样（边界值走逐字）。
2. `type_text("a" * 1001)` → **恰好 1 次** `insert_text`、**0 次** `press`、**0 次** `Keystroke` 采样、仍 1 次 `after_type`。
3. 分流命中日志恰好 1 行（`info`），含字符数；≤1000 时不打。
4. 全仓 grep：`type_horizon_chars` 只出现在 `utils/humanize.py`（平台不得复制常量）。
5. `fill(` 静态断言：除 YouTube `_fill_editable` 外该平台目录计数 = 0；文章平台的正文粘贴不计入（走 `navigator.clipboard` + `press("Meta/Control+V")`）。
6. 真机：TikTok 长配文（>1000 字）dry-run 到 ARM 就绪 → `exit 0`，日志出现 1 行分流记录；`HUMANIZE=0` 对照同结果。

### 置信度

- **用户决策**：长度分级、N=1000、`insert_text`、`type_text` 内部分流、预算/退出码/18 不动、文章流解阻。
- **代码明确**：TikTok 4000、yt `_fill_editable` 的 `#` 约束、文章正文粘贴、各平台 `fill` 调用点、15 分钟常数。
- **仅推断**：「粘贴比 insertText 更像人」的差值可忽略不计（无平台侧证据）；抖音/快手/视频号/百家号/支付宝的简介上限 ≤1000；1500 字长配文的实际出现频率。
- **需真机验证**：TikTok/Instagram 长配文 bulk 写入是否被编辑器接受（部分编辑器对一次 `insertText` 有长度截断）；`after_type` 后是否还需一次 DOM 静默（归 06）。

### 重开条件

- 若真机出现「bulk 写入被截断/被拒」→ 需重新评估阈值或改成分段写入（但仍不走剪贴板）。
- 若将来引入「按字段差异化阈值」的需求（例如极短的标题也要粘贴）→ 说明单例常量不足，需重开本票。
