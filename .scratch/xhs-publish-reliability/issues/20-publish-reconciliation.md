## Question

03 确认成功判据**保持现状**（只认 URL 命中 `publish/success`，观察窗直到预算耗尽），且点击后任何说不清的结局一律 `exit 9`。本票决定：是否在判不出结果时自动去「笔记管理」核对，把人工成本消掉。

需要确认：

1. **是否做**。只对 `exit 9` 做，还是成功路径也补一次终局确认？
2. **触发时机与窗口**。`exit 9` 之后隔多久查（平台侧可能有发布延迟）？查几次、间隔多少？是否受 15 分钟预算约束（预算此时已耗尽，等于要延长预算或另开一个对账预算）。
3. **匹配键**。标题精确匹配还是归一化匹配（全角/半角、空格、截断）？同名历史笔记怎么排除（发布时间窗口 + 封面 + 正文首段）？
4. **结果的出口**。找到确证 → 改判 `exit 0`？还是保留 `exit 9` 但在文案里写明「已确认存在」？两种对调度器意味着完全不同的重试决策。
5. **实现层**。放在提交链路内（延长 OBSERVE），还是 CLI 收尾的独立一步？独立一步意味着浏览器要活到对账结束。
6. **不可判定时**。存在同名但无法证明是本次发布 → 出什么？新增错误类型，还是退回 9？
7. **风险**。「发布成功后回后台翻列表」本身是不是一个更像脚本的行为？与 charter ① 的权重如何权衡（**标注置信度**）。
8. **依赖前提**。03 §9 的真机结论（定时发布是否跳转 `publish/success`）直接决定本票的收益：若定时发布每次都进 9，本票从「可选优化」变成「必需」。

产出：触发点 × 匹配键 × 出口 × 浏览器生命周期 的判定表。

## Answer

**决议：不做自动对账；本票移出范围，且不再评估。**

- **范围**：`exit 9`（含 FIRE 抛异常、OBSERVE 15s 超时）之后**不打开任何后台列表、不读发布结果接口**；成功路径（`0`）同样不做终局确认。
- **收尾保持现状**：`9` 的码表、文案、机器信号一律不动。`docs/CLI.md:198` 的「按标题 / 素材 / 发布时间人工核对」即权威指引；文案归 13、`publish_attempted` 归 07/18，本票不制造第二个权威来源。
- **理由（用户决策）**：**① 更像脚本**。发布后回「笔记管理」翻列表是典型的脚本行为，且要求浏览器活到核对结束、会话占用变长。charter ① > ②，故不做。
- **接受代价**：`9` 的人工核对成本留在调度方；定时发布若每次都进 `9`，该成本更高。这是调用方的排程选择（可少用定时），不是 CLI 的对账职责。
- **明确不做**：标题 + 时间窗 + 类型三态匹配、列表翻页、延迟重试窗口、`9 → 0/1` 改判、为对账延长浏览器生命周期、新增 `check` 之外的核对命令。
- **与上游关系**：`xpzouying/xiaohongshu-mcp` 也不做——`waitPublishSuccess` 只判 URL 离开，全仓只有 creator home 与发布页两个 creator URL，无 `note-manager` 导航、不读作品 ID / 发布结果接口（`research/01` §2，代码明确）。与上游一致**不是**理由，理由只有 ①。
- **重开条件**：**无**。除非整个 destination 重画（例如 charter ① 的优先级被推翻），否则不再评估；若将来平台在成功页/响应里直接给出作品 ID 或笔记链接，那是 03/05 的成功判据升级，不是本票复活。
- **对下游的影响**：抽掉 03 §9 #1 与 04 §6 里「收益见 20」的预期（两处已加注释）；18 的调用方契约不变（`9` 一律先核对、禁止自动重跑）。原依赖前提 #8（定时发布是否跳成功页）**不再阻塞本票**，仅剩频率意义。
- **置信度**：用户决策（不做 / 不再评估 / ① 优先）；代码明确（上游缺失、CLI 现状文案）；不再需要验证（原 #8）。
