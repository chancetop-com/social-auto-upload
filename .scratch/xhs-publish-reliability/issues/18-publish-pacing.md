# 18 — 发布节奏、失败冷却与熔断

## Question

决定“多久发一次、失败后多久再试、什么时候必须停下来人工介入”。这是封禁风险最大的单一杠杆，而现在项目里**只有调用方传的 `--not-before`，没有任何默认节流**。

1. **单账号最小发布间隔**：是否设默认值（如 ≥30min）？按账号类型（新号/老号）分级还是统一？调用方能否显式放宽。
2. **频次上限**：上游 README 的运营建议是单账号每天 ≤50 篇。是否采纳为硬上限？按小时还是按天？超出时是排队、拒绝、还是仅告警。
3. **失败冷却**：三类失败分别冷却多久——上传失败 / 平台明确拒绝 / 结果未知（exit 9）。exit 9 是否要求**人工确认后**才允许下一次（与 `PublishResultUnknownError` 的既有语义一致）。
4. **连续失败熔断**：N 次连续失败后暂停该账号多久？N 取几？熔断状态存哪。
5. **实现在哪一层**：CLI 无状态（每次进程独立）→ 必须有本地状态文件（`.local/`？）或交给调度 App。谁负责记忆、如何避免多进程竞争。（同一账号不并发，见 21；因此状态文件**不需要跨进程锁**。）
6. **与 04 的分工**：04 管“平台已经说限流时怎么办”，本票管“我们主动多久发一次”。两者不得互相覆盖。

## Comments

- 来自 04 的更新（2026-11-11）：04 已定**不做任何文案扫描**，因此“平台已经说限流”不会被单独识别（表现为 15s 未离开 → exit 9）。本票的主动节奏成为限流防护的唯一杠杆，第 3 项「失败冷却」需要覆盖“9 但实际是限流”的情形。

产出：节奏规则表（事件 × 冷却时长 × 是否需人工确认 × 超限动作）+ 实现层归属 + 状态存储方案。

## Answer

**决定（用户裁定，2026-11-11）：节流完全不属于 CLI。**

> 「不用管节流，这个由调用 App 去做。」

因此本票**不做**：本地状态文件、发布前节流预检、最小间隔等待、频次上限、失败冷却计时、连续失败熔断、相关 CLI 参数。原问题 1/2/4/5 全部随之作废（归调用方），**本规格不设任何默认数字**——间隔、日上限、阈值都是 App 的业务参数。

本票只落**两件事**：① 把「调用方拿到的信号」定义成规范契约（CLI 保证品）；② 补一个信号缺口（`10` 的点击前后歧义）。

### 1. 调用方契约（规范，进规格；`docs/CLI.md` 为派生投影）

CLI 给调用方的全部信号（码表不变，`docs/CLI.md:160` 仍是权威）：

| 信号 | 含义 | App 应采取的动作 |
| --- | --- | --- |
| `0` | 已发布；或 `--no-publish` 已准备完成 | 该账号发布计数 +1、记录时刻 |
| `1` | 确定未发布（含点击前超时、上传失败、平台拒绝） | 可无条件重跑（冷却另议，属 App） |
| `9` | 已派发，但未确认成功；**帖子可能已存在** | **禁止自动重跑**；先核对；确认未发才可重试 |
| `10` + stderr `publish_attempted=true` | 点击之后才落登录/验证页；**帖子可能已存在** | 先核对是否已发，再排人工登录 |
| `10`（无该行） | 点击之前就登录失效；**没有发布** | 排人工登录，登录后可直接重跑 |
| `11` | 桌面应用/Launcher 返回 429 | 退避重试（`docs/CLI.md:199`） |

- `9` 与「实际是限流」不可区分（04 已定不扫文案），故 `9` 的处置对两者都成立：停下、核对、不自动重跑。
- App **不得**把 `1` 与 `9`/`10+publish_attempted` 混为一谈而统一重跑——这是本契约存在的唯一理由。

### 2. 补 `10` 的点击前后歧义：一行 stderr，不动码表

- 触发条件：仅当**发布点击已置位之后**才检出登录/验证页（即 03/07 的 `publish_attempted=True`），CLI 在退出 `10` 时额外向 **stderr** 打**单独一行** `publish_attempted=true`。
- 退出码**仍是 `10`**（守住 07「不加新码」）；文案不变（13 的「发布可能已发出」后缀保留，供人读）。
- 点击前检出 `10` → **不打**该行（缺省即「未发布」，避免调用方把「没有这行」误读成未知）。
- 该行是**机器信号**：固定 token、无本地化、无前缀、不带时间戳。`docs/CLI.md` 的「机器信号只有退出码与 stderr」因此多一条具名契约。
- 实现落在共享层（15）：16 个平台同形；小红书先行。

### 3. `--not-before` 机制不动，只加一条使用约束

- 语义、预算顺延（`uploader/publish_timeout.py:90-104`）、参数全部不变。
- 契约里加一句：**不要用 `--not-before` 实现发布间隔或「一日多篇」排程**，改为定时调用 -- 它的等待发生在填表之后、点击之前，浏览器与（托管模式下）Profile 全程被占用（21 已定同账号不并发），长等待会直接卡住 App 自己的调度。它只用于「同一篇内容等到某个具体时刻」。

### 4. 事实更正（本票原前提）

上游 `xpzouying/xiaohongshu-mcp` README 原文是「根据本人实操，小红书每天的发帖量应该是 **50 篇**」——**作者个人经验值，不是平台规则**，不做任何依据（连「硬上限」都不够格）。本规格不据此设上限。

### 5. 对其它票的影响

- **04**：其「本票的主动节奏成为限流防护的唯一杠杆」需更正为**「唯一杠杆在 CLI 之外（调用方）」**；04 的空词表结论不变。
- **07 / 03**：`publish_attempted` 由「异常对象上的标志 + 中文后缀」升级为「异常对象标志 + 一行 stderr」；码表与文案均不变。
- **15**：该 stderr 行属共享层接口，16 个平台同形；迁移后其它平台的 `10` 也须区分点击前后。
- **16**：断言项 +1——点击前 `10` 的 stderr **不含**该行；点击后 `10` **含且仅含一行**。
- **21**：前提不变（同账号不并发仍由调度侧保证）；本票不引入任何跨进程状态。

### 6. 置信度

- **代码明确**：当前无任何节流代码；`--not-before` 的等待位置与预算顺延；`publish_attempted` 尚未存在于代码；退出码表。
- **用户决策**：节流归调用方、契约表、stderr 一行、`--not-before` 只加约束。
- **仅推断**：长 `--not-before` 占住 Profile 会卡住 App 调度（依据 21 的「同账号不并发」+ 托管 Profile 占用语义，未实测）。
- **需真机验证**：点击后落登录/验证页的真实频率（影响该 stderr 行的实际价值，但无论频率高低契约都成立）。

### 7. 重开条件

- 若将来要求 **CLI 自带节流**（例如无调度 App 的单机使用），本票重开，至少需要：状态文件位置与格式、原子写、账号键归一化（本地 `--account` vs 托管 `profile_id`）、`PACING=0` 快路、新退出码或等待语义。
- 若 `10` 的两种情形在真机上无法稳定区分（例如点击瞬间跳转导致 `publish_attempted` 置位不可靠），stderr 契约需重议。
