## Question

怎样让五批平台依次迁移，并同时保持未迁移平台、托管模式和发布结果契约稳定？托管模式仅包含启动契约票已批准的有头/无头配置来源调整，其余行为保持原样。

- 第一批怎样复用统一的本地持久化会话入口？小红书、Rednote 的登录、check、视频和图文有独立启动路径，需明确接入位置，不能只修改共享 `_local_session`。
- 中间批次如何区分已迁移与尚未迁移的本地调用方？临时兼容层何时删除，怎样避免共享变更导致第二至第五批被提前切换？
- 本地与托管的 headless 配置解析怎样随批次应用，覆盖显式值、未传参、已有 True 配置及内部预检，同时避免提前改变尚未迁移平台？托管忽略本地浏览器选择/路径且不专门报告的规则怎样落实？
- 哪些额外 context 是需要保留的匿名验证环境，哪些只是旧实现为了 UA 探测或重建 stealth context 而存在？按用途判断，不能统一删掉所有 `new_context`。
- 去掉语言设置后，不支持的界面或选择器失败如何给出明确错误，并与真实登录失效、验证页和发布后未知区分？不自动调整语言，也不要求新增完整多语言适配。
- 哪些初始化脚本是业务必需，哪些是指纹覆盖？如何让本地退出 stealth 路径，又不改变托管流程或遗漏仍使用辅助文件的入口？
- 统一 `no_viewport=True` 并移除额外最大化、固定 viewport 和无已知必要性的参数/权限后，哪些页面交互需要调整？保留已证实的站点剪贴板权限；其他确有业务必要的初始化或权限例外是什么？
- 每批需要哪些离线契约检查，最终四个平台的真实回归覆盖哪些用户流程？真实素材在执行时落实，其余平台和托管模式只做离线回归已确定。
- 默认 Chrome、按需启用的配套 Chromium、自定义可执行文件路径如何在各批保持统一接入并验证优先级、参数和错误契约？README 怎样覆盖 CI 环境按需安装 Chrome 或 Chromium 的方法？此处是文档要求，不增加 GitHub workflow 或完整浏览器实测矩阵。
- 怎样把生命周期票已定的按浏览器种类分目录、跨进程占用、首次迁移重启复验及定向 `reset-profile` 接入各批正式 CLI？自定义 executable 种类识别须在打开账号目录前完成；重建仅清明确指定的叶子目录并保留父级别名归属，不能提前改变未迁移平台。
- 怎样接入[账号别名与登录态校验](./05-account-binding-migration.md)已定的自由换号、旧身份旁文件退出和登录失效即结束当前业务？Instagram 不能继续从旧 Cookie 文件取得预期 ID；大鱼号、知乎、雪球同时退出历史绑定和为防中途换号而执行的账号前后比较，保留实际平台操作、显式目标与历史作品所需的信息和核验。清理验收需覆盖仅旁文件残留及部分清理失败，托管流程保持现状。
- README、安装文档、Agent Bootstrap、平台 skill、账号相关文档与打包配置在何时更新，确保每批发布时说明与实际行为一致？Chrome 和 Chromium 都已确定按需安装，迁移后的基础安装不得无条件要求任一种浏览器，需提供可选路线；分批期间仍须满足尚未迁移平台的现有依赖。

回答应形成可交给实施会话的接入规则、例外清单和分批验收标准。五批平台顺序已经确定，不再重新决定。

### 分批接入与兼容收口

- 第一批建立共享持久化能力，由已迁移调用方显式接入；旧本地会话入口继续服务尚未迁移调用方。不能把全局默认直接改成 persistent 后期待其他平台自然兼容。
- 一个进入当前批次的平台，其正式本地动作、内部预检和直接支撑这些动作的 uploader 路径一起切换：启动、状态读取、登录探测、写回与清理应成套迁移，不能留下部分命令读 JSON、部分命令读 Profile 的混合状态。
- headless 的“未传参”必须保留到统一解析层。已迁移平台的 CLI、直接 uploader 调用、login/check/发布/验证及内部探测使用本次解析结果；其托管动作也在同批采用已批准的 headless 默认来源。尚未迁移平台仍使用旧解析与默认，避免共享 parser、构造器或配置示例提前切换行为。
- 模式选择保留现有动作级路由：第一批 login 原有托管限制不变；Instagram verify/delete 即使存在托管环境变量仍为本地动作。不能用一个平台级开关覆盖这些例外。
- 托管分支继续走原 provider、CDP、所有权与断开流程；不进入本地来源识别、Profile 锁或文件清理。新增本地浏览器选择与路径按前置契约忽略；清理本地参数常量时保留托管原有传参与日志行为。
- 每批只为当前平台提供本地 reset-profile。它使用明确的清理种类，不经浏览器启动配置猜测目标；不能因该命令共用解析器而为 Bilibili 或未迁移平台提前开放。
- 旧资料迁移是一次性工作，完成后删除相关旧文件检测、重启复验、清理、重试、临时入口和迁移专用测试代码，保留执行记录及常规 Profile 行为回归；不能仅关闭功能开关后留存代码，也不在日常 login/session 中保留迁移分支。
- 第五批收口时核对全部正式 CLI 可达路径，确认上述一次性迁移代码已移除，并移除临时新旧分流、JSON 预检/导出和旧身份防错配逻辑。范围外入口仍使用的旧辅助代码、stealth 文件及包资源按实际引用保留；不据此扩大为历史入口重构。

### 大鱼号公开验证的资源关系

- 保持先在已登录主 context 中核对后台作品，再在显式 `--public` 时进行访客验证的流程。整个 verify 仍需要相应登录态，不能改成全匿名命令。

- 匿名 context 由验证步骤在成功、失败或取消时单独清理；主会话及 Profile 占用由外层所有者管理。匿名检查不能关闭主会话、重新争用同一 Profile，或启动另一来源的浏览器作为静默替代。

### 每批验收与错误边界

每批按实际改动做相关离线回归，覆盖以下可观察契约；不要求镜像实现的重复测试或完整笛卡尔组合。

- 正式动作实际到达新持久化入口；平台、别名和实际浏览器种类选对 Profile。自定义路径、两种 channel、headless 显式值/缺省值及内部预检传递到启动边界，不能只测 parser。
- 模拟缺少非选定浏览器时不受影响，选定来源失败不静默回退；托管忽略本地配置，未迁移调用方保持原参数和状态路径。
- 以旧 JSON/旁文件缺失、损坏或记录不同主体等场景验证新本地流程不依赖它们；模拟 Profile 有效而旧文件不存在，正式动作仍可进行。一次性迁移执行前另验证仅旁文件残留、部分删除失败及重试；完成后删除迁移专用实现与测试，最终回归验证日常命令不会读取或清理重新出现的旧文件，也不会为它们增加重启。
- 按生命周期票检验同 Profile 独占、不同种类隔离、初始化失败、取消、关闭失败和定向 reset；迁移重启复验仅在一次性迁移执行前验证。业务代码不得自启同目录，发布后的错误优先级和禁止自动重发契约保持。
- 登录正向证据、明确未登录/验证码与页面探测故障分别处理。选择器失败应报告平台、动作、失败步骤等有据诊断，不能凭失败推断语言不支持或登录失效；提交后继续按原发布结果契约处理。
- 校验本地去除指纹与语言设置、保留业务操作；相关页面的滚动、iframe/popup 和小窗口场景按现有能力验证。第五批检验匿名 context 无账号状态、清理顺序与文章剪贴板用途。
- 托管只做离线回归；保持 provider 参数、所有权、错误与既有日志，唯一默认行为调整为已批准的 headless 来源。最终正式路径收口检查还须覆盖范围外调用方所需资源没有被误删。
