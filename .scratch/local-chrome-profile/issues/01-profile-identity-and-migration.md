# 本地 Profile 的身份与旧登录态迁移

Label: wayfinder:grilling
Type: grilling
Status: resolved
Blocked by: —
Assignee: Codex（本会话）

## Question

为本地 Chrome 持久化 Profile 确定唯一的身份与状态来源，避免登录、检查和发布分别使用不同的浏览器身份。

- Profile 如何按平台和 `--account` 定位，目录放在哪里，账号名称中的路径字符如何处理？建议项目专用目录，不使用用户日常 Chrome 的默认目录。
- 只有旧 Cookie JSON 的用户是重新登录，还是支持一次性导入？是否保留旧文件作为备份，后续命令还会不会读写它？推荐重新登录、保留旧文件、不反复导入；这是建议，尚未决定。
- Profile 目录存在但登录失效，与 Profile 尚未创建分别如何处理？原来基于 JSON 的 CLI 文件存在检查、平台 Cookie 预检如何退出？
- Facebook Page 等目标身份与登录账号不同的场景，Profile 绑定登录账号还是发布目标？如何保留已有账号复用语义？
- 哪些状态属于可跨运行复用的 Profile，哪些是单次运行状态？异常退出留下的浏览器状态如何解释，是否保留 Cookie JSON 导出用途？

回答应给出身份映射、迁移行为表与用户可见结果，不实现迁移工具。

## Comments

- 用户修正备份建议：“按建议但是旧的不保留”。旧 JSON 不作为迁移备份保留；删除时机和分批迁移边界待下一轮确认。

### 2026-11-17 — 第二轮用户决定与待澄清项

- 新 Profile 首次登录验证成功后删除该平台、该账号的旧 Cookie JSON，不创建备份。验证成功前暂留旧文件但已迁移流程不读取；尚未迁移的平台继续原有行为。
- 删除失败明确报错，并允许重试清理；不撤销已成功建立的 Profile 登录。
- 用户询问 Facebook 与 Facebook Page 原来是否隔离；尚未确认未来 Profile 的共享或隔离政策。当前正式 CLI 自动选择不同 JSON 路径，发布目标 `--page` 独立于登录身份。

### 2026-11-17 — 第三轮用户决定

- Profile 按平台与 `--account` 隔离，Facebook 与 Facebook Page 继续保留两个独立 Profile；同一 Facebook Page 登录账号下的多个发布目标不再拆分 Profile。
- 已迁移本地流程统一状态规则：只有 `login` 引导登录；`check`、发布与验证遇到未建 Profile 或明确未登录时退出 `10`，提示执行 `login`。目录存在不证明已登录。

- 保持发布提交边界与禁止自动重发契约。

### 2026-11-17 — 第四轮用户决定与待澄清项

- Profile 是已迁移流程的唯一登录态来源，不再导出 Cookie JSON。
- Cookie、站点存储和浏览器偏好跨运行保存；页面对象、任务进度、是否已提交不用于恢复后自动续跑。
- 真实账号身份记录与发布结果文件继续保留，不随旧 Cookie JSON 一起删除；平台身份绑定迁移另列决策票。
- 用户询问旧账号命名方式；`browser_profiles/<平台>/<账号哈希>/` 仍是建议，尚未决定。当前 helper 直接拼接 `cookies/<platform>_<account>.json`，仅检查账号非空，未统一归一化或处理路径字符。

### 2026-11-17 — 可读账号目录

### 2026-11-17 — 当前代码依据

## Answer

### 身份映射

- 使用项目专用的 `browser_profiles/`；不使用或改写用户日常 Chrome 的个人资料。账号目录仍按 `<平台>/<账号名>/` 定位，账号目录内的最终浏览器目录划分由[本地 Profile 的生命周期与并发占用](./03-profile-lifecycle-and-concurrency.md)细化。整个根目录不纳入版本控制，忽略规则已在生命周期会话按用户要求落实。
- 平台取现有正式 CLI 的标准平台名，账号取 `--account` 原值。同一平台、同一账号、同一浏览器种类的登录、检查、发布、验证及其他正式本地浏览器入口必须定位到同一 Profile；种类选择与切换规则以生命周期票为准。
- 目录直接显示账号名，不使用哈希，不自动裁剪、改大小写、做 Unicode 归一化或替换/转义字符。中文等正常名称保留；账号必须是单个安全目录名，拒绝空白名称、路径分隔符、`.`、`..` 等会改变路径含义的输入。文件系统不支持时明确报错，不能悄悄换名字。
- 用元数据记录平台和原始账号标签，核对已有目录归属；文件系统把不同大小写或 Unicode 写法映射到同一路径时，原始标签不符即报冲突，不自动合并。目录解析还须保持在项目专用根目录内。
- 不同平台或账号各自隔离。Facebook 与 Facebook Page 保留不同账号目录，例如 `browser_profiles/facebook/main/` 与 `browser_profiles/facebook-page/main/`，其中的浏览器 Profile 也互相隔离。Facebook Page 的 `--page` 是发布目标；同一登录账号管理多个 Page 时复用其所选种类的 Page Profile。
- 账号标签是账号别名，不固定对应平台真实账号；换号、登录失效及旧身份资料的退出规则以[账号别名与登录态校验](./05-account-binding-migration.md)为准。

### 登录态与其他状态

- 已迁移本地流程以本地浏览器持久化 Profile 为唯一登录态来源，默认优先 Chrome，保留按需启用的 Chromium；不导入旧 Cookie JSON，也不再以旧 JSON 恢复、预检或导出登录态。原 JSON 文件存在检查和 Cookie 内容预检须随对应平台切换，不能在 Profile 已有效时仍阻止命令执行。
- Cookie、站点存储、浏览器偏好可跨 Browser session 保存。页面对象、任务进度、内存中的提交状态属于单次运行；异常退出留下的浏览器数据不代表任务成功，也不是自动续跑或重发的依据。
- 旧身份旁文件、发布结果 JSON 与 Cookie JSON 是不同用途的资料，不做后缀相同即批量删除；旧身份文件退出、历史结果保留的规则详见[账号别名与登录态校验](./05-account-binding-migration.md)。资料元数据不得成为另一份登录态副本。
- 本轮不提供 Cookie JSON 导出能力，也不从旧文件提取真实账号标识；具体平台规则见上述决策。

### 迁移行为表

表中旧资料复验、删除与失败重试仅描述一次性迁移作业。迁移完成后移除该作业及相关运行代码；常规 login、check、发布、验证不再探测或处理旧文件。正常 Profile 登录与复用继续保留。

| 情形 | 行为与用户可见结果 |
| --- | --- |
| 平台尚未进入迁移批次 | 保留原有本地 JSON 行为；共享层改动不得提前切换或清理该平台。 |
| 已迁移平台只有旧 Cookie JSON | 不导入、不据它判断已登录。用户执行该平台的 `login --account <账号>`，在新 Profile 中重新登录。 |
| 尚未创建 Profile | `login` 创建专用 Profile 并引导登录；其他依赖登录的本地命令退出 `10`，明确提示尚未建立登录态及对应 login 命令。 |
| 目录存在，但首次登录未完成或平台明确未登录 | 目录存在不视为登录成功。`login` 继续登录；其他依赖登录的命令退出 `10`，提示完成/恢复登录。无法可靠判断的探测故障不归入此行。 |
| 已有有效 Profile | 登录、检查、发布、验证等复用该 Profile，各自检查登录状态及实际操作要求的目标，不增加账号前后比较，不依赖旧 Cookie JSON。 |
| 首次登录取消、失败或未通过验证 | 不删除旧 Cookie JSON；已迁移流程仍不读取它。留下的 Profile 数据不被视为成功标记；其恢复和清理方式由生命周期票决定。 |
| 一次性迁移中，新 Profile 登录验证成功 | 按生命周期票及[账号别名与登录态校验](./05-account-binding-migration.md)完成重启复验后，清理明确匹配的旧资料，不创建备份；不能仅检查目录或文件存在，也不以历史账号相同为前提。 |
| 一次性迁移中，旧 Cookie JSON 删除失败 | 明确报告清理失败，按普通文件操作故障处理；保留已成功的 Profile 登录。在迁移阶段重试验证与清理，不要求再次建立登录态，也不回退到 JSON；不留下日常 login 的自动重试分支。 |
| Profile 登录已失效 | `login` 恢复；检查、发布、验证等退出 `10`，提示登录。不得把 Profile 缺失、明确失效和未知故障合成一个“invalid”。 |
| 网络、页面结构、权限、Profile 损坏或目录身份冲突 | 明确报对应故障，退出 `1`；不推断为登录失效，不自动删除/重建 Profile。非法账号参数仍遵循用法错误契约。 |

删除只针对当前平台、当前别名明确匹配的旧资料；旧身份旁文件的清理范围见[账号别名与登录态校验](./05-account-binding-migration.md)。不清空整个 `cookies/`，不处理其他平台、别名或历史结果。旧路径若不能安全、唯一地定位，应报告具体清理问题而不是猜测删除目标。用户选择保留可读原名，未请求自动改名或批量迁移旧账号标签。

### 状态与边界

- 只有 `login` 引导登录。已迁移平台的本地未登录/登录失效统一使用 `10`，这是对部分现有本地 CLI 行为的调整；运行或探测故障使用 `1`。识别到人机验证时保留现有 `reason="verification"` 与补救提示，不混淆成普通未登录。
- 真实发布后的 `publish_attempted`、结果未知及禁止自动重发契约保持不变。清理旧 JSON 不是发布重试条件；不能因本地 Profile 的状态看似恢复而重新提交。
- MLX / AdsPower 的启动、连接、Profile、登录态及退出行为不变；Bilibili 不参与迁移。
- 本票只记录决策，不实现迁移或删除实际账号文件。后续由[本地 Profile 的生命周期与并发占用](./03-profile-lifecycle-and-concurrency.md)处理占用、关闭、异常退出与恢复，由[账号别名与登录态校验](./05-account-binding-migration.md)处理平台身份例外，再由[分批接入的共享边界与平台例外](./04-platform-integration-boundaries.md)收敛分批实施规则。
