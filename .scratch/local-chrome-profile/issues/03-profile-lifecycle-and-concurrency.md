# 本地 Profile 的生命周期与并发占用

Label: wayfinder:grilling
Type: grilling
Status: resolved
Blocked by: 01, 02
Assignee: Codex（本会话）

## Question

同一 Profile 跨命令复用时，如何明确浏览器所有权、占用冲突与退出后的状态？

- 同账号同时执行 check、上传或验证时，是立即报占用还是等待？建议立即报错；锁粒度、跨进程竞争和异常退出后的恢复必须一致。
- 如何区分本项目进程占用、用户手动打开专用 Profile 与 Chrome 自身的目录锁？不依赖粗暴删除 Chrome 锁或结束其他浏览器进程恢复。
- 用户按需切换 Chrome 与 Chromium 时，已有同平台、同账号 Profile 如何处理？是否允许跨浏览器直接复用需要有兼容性依据；不能因切换浏览器而静默改用另一账号身份或覆盖已有状态。
- 自定义可执行文件路径优先于浏览器选择已由启动契约票确定；更换路径、实际浏览器或版本是否视为同类切换，Profile 元数据如何识别实际运行来源？不能仅凭 `LOCAL_BROWSER` 或旧配置名中的 CHROME 判定兼容性。
- `launch_persistent_context` 返回 context，关闭它即结束对应浏览器；共享 `BrowserSession` 应如何表达和清理资源，避免重复关闭或漏关？托管所有权语义保持原样。
- Profile 自然保存状态，已不同于现有成功后导出 JSON 的方式；失败、取消、超时、登录失效之后哪些状态保留，是否需要明确的恢复入口？
- 发布结果未知时如何关闭本地资源并保留现有退出语义，保证不因恢复浏览器而重发？

回答应描述生命周期与冲突契约，不实现锁或重试机制。

## Answer

### Profile 身份、目录与浏览器选择

一次本地浏览器 Profile 的完整定位为**平台 + 原始账号标签 + 浏览器种类**。账号命名、目录归属、路径边界和 Facebook / Facebook Page 隔离规则继续遵循[本地 Profile 的身份与旧登录态迁移](./01-profile-identity-and-migration.md)；本票将其目录布局细化为：

```text
browser_profiles/<平台>/<账号>/chrome/
browser_profiles/<平台>/<账号>/chromium/
```

- 两个叶子目录分别是传给 `launch_persistent_context` 的 `user_data_dir`，各自拥有完整的浏览器数据；父账号目录不是浏览器 user data directory。不能把 Chrome 内部的 `Default` 子目录再当作这里的 Profile 根目录。
- `chrome` / `chromium` 表示实际浏览器种类，不按系统安装、自定义路径、版本号或 headed/headless 再分目录。Chrome 的两种路径入口复用 Chrome Profile；Chromium 的两种路径入口复用 Chromium Profile。
- 先按[本地 Chrome 启动参数与失败契约](./02-chrome-launch-contract.md)选定实际启动来源，再识别种类并定位 Profile。`LOCAL_CHROME_PATH` 非空时优先；路径指向 Chromium 即使用 `chromium/`，不能因默认 `LOCAL_BROWSER=chrome` 而打开 `chrome/`。
- Chrome ↔ Chromium 切换只选择另一目录。首次使用由 login 建立登录态；非 login 命令遇到该种类的 Profile 未建立时仍退出 `10`。已有对应 Profile 则继续验证并复用，不复制、迁移或清除另一种浏览器的状态。
- 同种浏览器改路径、更新版本、改有头/无头不触发重建。版本变化本身也不是自动清空的理由；不承诺降级或任意构建兼容，无法运行时按真实故障退出 `1`，不自动清空、回退或切换种类。
- 两个 Profile 的账号别名相同不代表真实账号相同；换号及登录失效边界以[账号别名与登录态校验](./05-account-binding-migration.md)为准，不再共享长期绑定记录。

### 种类识别与元数据

- 标准 Chrome / 配套 Chromium channel 在未被路径覆盖时提供已知种类。自定义路径在打开任何账号 Profile **之前**读取目标产品信息；普通 macOS/Linux 发行包可用 `--version` 的产品名，Windows 可读取 executable 的产品资源。依据及限制见[生命周期研究](../research/profile-lifecycle-evidence.md)。识别过程不传账号目录，不通过启动既有 Profile 来试错。
- 文件名、路径中是否有 chrome、配置名中的 CHROME、UA、CDP 的 `Chrome/<version>` 均不能单独证明实际种类。识别不到或信息冲突时退出 `1`，说明无法识别所选 executable，提示修正为可识别的 Chrome/Chromium 可执行文件；保持原 Profile，不猜测也不要求用户因 unknown 重建。
- 元数据区分平台、原始账号标签、浏览器种类与诊断信息。记录有效启动来源、用户指定路径、可可靠取得的解析路径和版本；未知的实际路径或版本明确记未知，不拿配套浏览器预计路径冒充 channel/custom 实际路径。版本用于诊断，不作为自动重建开关。
- 已有目录的账号归属或种类元数据冲突、缺失或损坏属于故障，不能默认为当前请求的身份；未创建与创建失败的状态也不能当作登录成功。来源记录在互斥保护下更新，不允许一次失败的异种启动覆盖原有归属。

### 占用与跨进程生命周期

- 按实际 Profile 目录互斥：同一平台、别名、种类的 login、check、发布、验证和 reset-profile 一次只允许一个命令；占用立即退出 `1`，不等待、不自动重试。不同 Profile 可并行，包含同别名的两种浏览器目录；父级别名归属元数据仍须安全创建和核对，但不存在需要协调的共享真实账号绑定。
- 目录别名和等价路径不能绕过互斥。互斥从需要创建或读取 Profile 归属之前持有，覆盖启动、内部预检、业务操作、关闭和最终状态处理；首次迁移的关闭与重启复验之间不释放。内部预检不得再次启动同目录或重新竞争自己的占用权。
- 锁的有效性须由跨进程互斥原语维持；PID、时间戳及锁文件是否存在仅作诊断，不能凭残留文件永久判占用或直接删除文件接管。锁与重建目标分离，重建不能把自己的互斥保护一并删除。
- 本项目持有者、外部手动打开的浏览器及无法可靠分类的启动故障分别报告已知事实。提示可包含 Profile 路径和可验证的持有者信息，不包含 Cookie 等登录凭据。无证据时不宣称“被另一个进程占用”或“已登录失效”。
- 应用不通过删除 Chrome 的 singleton 锁、杀其他浏览器或接管用户手动打开的实例来恢复。应用互斥不能控制所有外部进程；浏览器仍有自己的占用机制，不能承诺其底层实现绝不执行原生恢复逻辑。
- 崩溃后应用占用可随进程结束释放，但浏览器子进程可能仍存活；下次命令仍须处理真实占用。需要用户先关闭残留浏览器时明确指出，不能通过等待超时或 PID 记录过旧擅自清锁。

### 会话所有权、退出与状态保留

- 本地 persistent context 是本次浏览器的生命周期资源，正常关闭该 context 即关闭对应浏览器。会话所有者负责集中、可重复安全调用的清理；被注入 session 的 uploader 不另行关闭外部交给它的会话。正常路径不再顺序重复关闭同一个 persistent context 及其已关闭的 browser。
- 资源取得后立即进入清理保护，覆盖 context 初始化、业务脚本、平台 setup 失败等部分初始化路径，不能只保护 yield 之后的业务。正常完成、失败、取消、超时和登录失效均尝试清理；取消继续传播，不能因清理吞掉中断。
- 清理失败须报告并尽力处理仍由本次会话拥有的资源，不无限等待或按进程名结束浏览器。硬终止、断电等情况不承诺 finally 一定执行、浏览器一定关闭或最新状态一定落盘。
- Cookie、站点存储与偏好保留浏览器已写入的状态。失败不自动回滚、删目录或重建；下次 login 可以继续恢复登录。目录存在或关闭事件均不是登录成功证据。
- 浏览器遗留的页面、草稿、任务进度不用于自动恢复执行；发布入口仍从正常流程开始并执行已有核验，不能根据 Profile 的可用性推断上次未提交或可以重发。
- MLX / AdsPower 的所有权、停止与断开行为保持原样，不使用本地目录锁、不因本地 persistent context 方案关闭托管 context；已批准的 headless 默认来源变化仍由启动契约票约束。

### 一次性迁移与旧 Cookie JSON 清理

为满足“新登录态可独立恢复后再删除旧资料”，仅在一次性迁移阶段，对待清理旧 Cookie JSON 或旧身份旁文件的账号执行以下顺序，并全程持有该 Profile 的占用权。这是临时迁移编排，不是常规 login 的长期能力；旧身份旁文件范围及核验语义以[账号别名与登录态校验](./05-account-binding-migration.md)为准：

1. 在所选种类的 Profile 中完成登录，取得平台正向登录证据，不增加账号一致性核验。
2. 正常关闭本次 persistent context；关闭失败则停止验收，不删除旧 JSON。
3. 使用同一浏览器种类、同一目录和同次请求的启动配置重新打开，复验平台登录状态，不借助旧 JSON、不自动再次引导登录，也不比较前后账号。
4. 复验通过并再次正常关闭后，才按上述别名决策清理该平台、别名对应的旧资料；不创建备份。删除失败报告文件操作故障，保留已建立的 Profile，在迁移阶段重试验证与清理，不留给后续日常 login 自动处理。

任何一步失败、取消或无法可靠判断，均保留尚未删除的旧资料，但已迁移流程仍不读取它。第二次打开明确未登录时提示再次 login；网络、登录探测、页面结构或关闭故障不伪装成登录失效。换号及登录失效边界见[账号别名与登录态校验](./05-account-binding-migration.md)。

一次复验只证明当时可恢复，不承诺以后永不失效。迁移完成后删除旧资料定位、检测、重启复验、清理、重试及其临时入口代码，不保留永久迁移工具、配置开关或基于旧文件存在性的触发分支。后续 login、check、发布、验证和浏览器切换均只处理 Profile；重新出现旧文件也不触发迁移。两个种类的 Profile 始终各自建立登录态，不从另一种类复制凭据。正常关闭与重新打开的持久化测试仍应保留，它们不要求运行时保留旧资料迁移代码。

### 显式重建入口

新增本地命令，规划形式为 `sau <平台> reset-profile --account <账号> --browser-kind chrome|chromium`。浏览器种类是明确的**清理目标**，不使用本次启动配置去隐式选择待删除目录；因此清理不要求安装或启动任何浏览器。

- 明确指定一个平台、账号和种类；只删除对应的浏览器 Profile 叶子目录及其专属状态，不清空父账号目录，不清另一种类的 Profile。完整路径校验、账号归属和占用检查适用于删除；目录越界、身份冲突或仍被占用时拒绝执行。
- 此命令的显式调用就是清除意图，不把普通 login、浏览器切换或故障处理变成隐式重建，也不额外要求交互式确认或新增备份流程。清理前后明确显示所选目标与操作结果。
- 清理完成后退出 `0` 并提示该平台的 login 命令，由用户重新登录；不启动登录、不预先创建一个看似有效的 Profile、不续跑任何发布。目标目录不存在时视为已清空，同样提示 login。
- 清理不保留旧 Profile 备份，也不清除父级别名归属、发布结果、另一种浏览器状态或其他别名资料。旧 Cookie 及旧身份旁文件的删除仍只由上述迁移验收触发，不由 reset-profile 顺带删除。
- 删除失败退出 `1`，指出未完成清理；不得报告成功或把部分删除的数据作为有效 Profile 继续使用。允许用户修复权限/占用后重跑同一显式清理，不能以恢复发布作为补救动作。
- 这是本地操作，不能用于托管 Profile；托管模式下拒绝该新命令并说明用途，不调用 provider 的删除、启动或停止接口。具体命令接入随各平台迁移批次提供，Bilibili 不增加此入口。

### 错误优先级与验收边界

- 参数缺失或非法仍为用法错误 `2`；占用、识别/元数据/运行故障、清理失败为 `1`；非 login 命令遇到所选 Profile 缺失或明确未登录为 `10`。人机验证保持原有 reason 与补救提示。
- 已有业务失败和发布结果优先于后续普通清理异常：结果未知仍为 `9`，登录/验证及 `publish_attempted` 保持原语义；已经确认发布成功时，关闭故障只能作为独立警告，不能改成可安全重试的失败。首次迁移 login 的关闭失败则不能满足成功验收或删除旧 JSON。
- SIGKILL、浏览器崩溃、清理失败、重建和重新登录都不是自动重发依据；本票不改变提交边界和禁止自动重发契约。
- 离线验收须覆盖同目录跨进程竞争、不同种类分目录、占用与锁残留区分、初始化/取消/关闭失败、来源识别与路径优先级、切换后独立复用、定向 reset 及部分失败，并验证托管行为与发布结果不被覆盖。两阶段登录复验与旧资料清理在一次性迁移执行前验证，迁移后删除专用实现和测试，保留执行记录及正常 Profile 回归；最终核对旧文件不会再次触发迁移。具体平台接入和批次清单交由[分批接入的共享边界与平台例外](./04-platform-integration-boundaries.md)。
