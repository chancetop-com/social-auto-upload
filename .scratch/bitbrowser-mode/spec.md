# 比特浏览器托管模式

Status: ready-for-agent

## Problem Statement

运营者已经在比特浏览器桌面端配置好窗口，并登录了要发布内容的平台。现有 `sau` 能接管 AdsPower 和 Multilogin X 的 Profile，却无法用比特浏览器的窗口 ID 复用这些登录态。运营者即使只想检查账号是否仍然在线，也得换一套浏览器资料。

同一个窗口还可能同时登录 TikTok 和 Instagram。调度方需要知道两条命令能否各自编辑草稿、谁负责关窗，以及一次失败后能否重跑。尤其在发布动作已经派发时，误判一次断线就可能重复发帖。

## Solution

运营者在本机比特浏览器中启用 Local API 和 Token 鉴权，打开目标 Profile，登录平台并复制窗口 ID。调用方把 Token 放入进程环境变量 `BITBROWSER_API_KEY`，把复制的 ID 传给 `--profile-id`。例如，`WINDOW_ID` 存放该 ID 时，运行 `sau tiktok check --profile-id "$WINDOW_ID"` 即可检查登录态。已登录时 stdout 仅输出 `valid`，退出码为 `0`。

| 平台 | 登录检查 | 视频发布 | 图文发布 | 可用 `--no-publish` 的发布入口 |
| --- | --- | --- | --- | --- |
| 大陆版小红书、Rednote、TikTok、Instagram | `check` | `upload-video` | `upload-note` | 视频、图文 |
| Facebook 个人、Facebook Page | `check` | `upload-video` | `upload-note` | 无 |
| YouTube | `check` | `upload-video` | 无 | 无 |

窗口关闭时由 CLI 打开，已打开时直接加入。同一窗口允许不同平台并行，同一平台的检查和发布合计限一条。每条命令在新标签页工作，分别报告结果。**最后一条已加入的命令离开时关闭整个窗口，包括用户从桌面打开的原标签页。**

## User Stories

1. 作为运营者，我希望使用桌面端复制的窗口 ID，以便在已经登录正确账号的 Profile 中工作。
2. 作为调度方，我希望通过环境变量选择比特浏览器，以便沿用现有平台命令和参数。
3. 作为在客户端改过端口的运营者，我希望能指定 Local API 地址，以便 CLI 连接到我的桌面客户端。
4. 作为维护多种托管凭据的调度方，我希望凭据冲突在打开窗口前就报错，以便知道要从环境中移除哪个变量。
5. 作为运营者，我希望能对七个平台分别运行登录检查，以便知道哪些 Profile 需要人工处理。
6. 作为内容发布者，我希望使用现有的视频和图文命令，以便保留每个平台已有的素材、编辑和结果约定。
7. 作为内容发布者，我希望在支持发布前停止的平台读到准备结果，以便在没有提交作品的情况下检查草稿。
8. 作为运营者，我希望指定无头或有头启动，也能省略开关直接加入桌面窗口，以便兼顾后台调度和人工编辑。
9. 作为运营者，我希望显式模式与已开实例不兼容时收到原因，以便保留正在使用的窗口和草稿。
10. 作为调度方，我希望两个不同平台同时申请关闭的窗口时只打开一次，以便两条命令使用同一次浏览器运行。
11. 作为多平台运营者，我希望 TikTok 和 Instagram 各自在新标签页编辑，以便其中一条命令结束或等待发布时间时，另一条仍能操作自己的草稿。
12. 作为调度方，我希望占用同一窗口和平台的第二条命令立即报告占用，以便在它开页前重新安排任务。
13. 作为多账号运营者，我希望同一平台能同时使用两个不同的 Profile，以便分别执行两个账号的任务。
14. 作为桌面用户，我希望在仍有 CLI 使用窗口时可以继续查看原标签页，并知道何时整个窗口会被关闭，以便安排手工操作。
15. 作为调度方，我希望在启动回包丢失或所有 CLI 被强杀后能识别当前窗口，以便从新页恢复工作，保留旧草稿和已有结果供核对。
16. 作为调度方，我希望上一次关闭尚未完成时得到有界的等待和明确的诊断，以便决定何时再次启动。
17. 作为运营者，我希望从错误中看出失败的操作，并能安全地分享日志，以便排查地址、Token、窗口 ID 或调试连接问题。
18. 作为调度方，我希望区分 API 限流、登录失效和人机验证，以便分别安排退避、重新登录或人工验证。
19. 作为调度方，我希望知道发布动作是否可能已经送达，以便先核对作品，再决定是否重跑。
20. 作为调度方，我希望清理页面或关窗失败时仍可取得主操作结果，以便单独处理残留窗口。
21. 作为维护者，我希望离线结果和真实客户端的实测记录可分别追溯，以便准确说明某个入口验证到了哪一步。

## Implementation Decisions

### 选择模式与识别 Profile

- 沿用 AdsPower 的职责划分。窗口目标持有复制的字符串 ID，HTTP 客户端负责比特浏览器的请求、响应与脱敏，Managed browser provider 向共享会话层提供窗口状态、资源身份、CDP 连接地址和异步关闭能力。CLI 在现有 `resolve_managed_provider` 接入选择逻辑。平台上传器继续通过 `browser_session` 使用该 Profile 唯一的现有 Chromium 上下文。Profile 中的 Cookie 和站点存储是登录态来源。
- 对使用浏览器凭据的入口，先解析 CLI 参数，再将 `BITBROWSER_API_KEY`、`ADSPOWER_API_KEY`、`MLX_API_TOKEN` 分别去除首尾空白。全部为空时走本地模式，仅一个非空时选择对应提供方。任意两个或三个非空时在命令分发前退出 `1`，列出冲突的变量名，向桌面服务发送零个请求。帮助及参数解析错误沿用现有行为。
- 比特浏览器模式要求非空的 `--profile-id`，去除首尾空白后按原字符串传给 API 的 `id`。缺失或空白退出 `2`。展示序号 `seq` 和窗口名称不参与查找。`--folder-id` 可省略，传入时静默忽略。`--account` 可省略，传入时沿用托管模式的忽略规则，身份和结果标签取自 Profile。`--debug` 保持上传器原有含义。
- `BITBROWSER_API_BASE` 仅在选中比特浏览器后读取。未设、空串或纯空白使用 `http://127.0.0.1:54345`。使用与 AdsPower 相同的地址校验和规范化规则，非法地址在发送请求前退出 `2`。仅设置地址不能激活托管模式。
- 桌面 Local API 请求使用 POST、JSON 和 `x-api-key` 请求头。`/health` 检查本机服务连通性，窗口状态单独按 ID 查询。业务响应读取 `success`，成功时读取对应的 `data`，失败时使用可获得的脱敏 `msg`。Token 不进入命令行、日志、异常、结果或对象的可打印表示。

### 冷启动、加入与归还

| 窗口状态或事件 | 调用方可依赖的行为 |
| --- | --- |
| 两条命令同时申请 | 共享层按同一操作系统用户、提供方和窗口 ID 协调，核对规范化的 Local API 地址。平台占用覆盖整条命令。同平台的后来者开页前退出 `1`。不同平台串行核对窗口状态，确认空闲且无待确认的启动后，合计只发一次 `/browser/open`。小红书与 Rednote 分开计数，Facebook 个人与 Facebook Page 分开计数。 |
| 冷启动 | 发请求前记录启动中。显式 `--headless` 或 `--headed` 优先，省略时读取 `LOCAL_CHROME_HEADLESS`，缺省为有头。有头按 ID 普通打开。无头另传 `args=["--headless"]` 和 `ignoreDefaultUrls=true`，省略 `newPageUrl`。从成功响应的 `data.ws` 取得浏览器级连接，记录本次请求的模式。窗口预设可能影响实际可见性，冷启动无需检查屏幕。 |
| 桌面已开或已有同行 | 在存活进程查询结果中核对窗口 ID（可使用 `/browser/pids/alive`），通过 `/browser/ports` 取该 ID 的调试端口，再读取 CDP 的 `/json/version` 取得浏览器级 WebSocket 地址。已有同行时核对地址摘要。进程、端口、连接或共享记录相互矛盾时，在开页前退出 `1`，保留窗口。加入成功复用唯一现有上下文，每条命令另开新页，共发零次打开请求。 |
| 加入时指定显示模式 | 省略开关可加入模式未知或与本地默认值不同的实例。显式开关优先与实例报告的模式核对，缺失时仅可采用对应同一浏览器连接的共享记录。匹配则加入，冲突或无法确认则在开页前退出 `1`，保留现场。 |
| 启动中断或回包丢失 | 后继命令观察到可连接的当前实例时从新页加入。若上次启动的结果仍不明，保留启动记录并报告原因，即使暂时查不到调试端口也不补发打开或关闭请求。 |
| 一条命令先离开 | 清理该命令的新标签页及能确认由这些页面打开的子窗口，断开自己的 CDP 连接。同一窗口仍有同行时，关闭窗口的 API 调用次数为零。同行的编辑页及桌面原标签页继续可用。 |
| 最后一条已加入的命令离开 | 直接以原窗口 ID 调用一次 `/browser/close`。关闭前不再核对实例。因此，若用户在旧命令运行期间从桌面关窗并重开同一 ID，末条旧命令可能关闭新窗口。 |
| 关闭后再冷启动 | 按异步关闭处理。再次冷启动须在关闭后至少等待 5 秒，且已确认旧进程退出。共享层在有界等待内仍无法确认停止时，向新命令报告原因。 |
| 所有 CLI 被强杀 | 下一条命令重新确认当前实例，包括桌面已重开同一 ID 的情形。使用新标签页开始，保留已落盘结果，不续点旧草稿。可能已提交的作品先由调度方核对。 |

### 结果与诊断

| 退出码 | 外部可观察的结果 |
| --- | --- |
| `0` | 主操作成功。`check` 的 stdout 仅有 `valid`。发布和发布前停止保留各平台现有结果格式。 |
| `1` | 凭据冲突、平台占用、服务不可达、Token 被拒、窗口不存在、发布前 CDP 连接失败、窗口模式无法确认或冲突，均给出对应诊断。HTTP 200 且 `success=false` 或无法识别的业务响应也归为 `1`，即使文案含“请求频繁”。平台登录探测本身出错也归为 `1`。 |
| `2` | 参数解析错误、缺少有效窗口 ID 或所选模式的地址格式非法。在接触窗口前结束。 |
| `9` | 已派发发布动作，随后断线或无法确认提交结果。调用方先核对作品，禁止自动重发。 |
| `10` | 平台要求登录或人机验证，沿用平台现有分类。若已经派发发布动作，stderr 额外输出独立一行 `publish_attempted=true`，调用方先核对作品。派发前的 `10` 和其他退出码均无该行。 |
| `11` | 探测、查询或启动实际收到 HTTP 429，CLI 立即返回，由调度方退避。 |
| `130` | 用户中断，按现有共享规则释放本命令占用。 |

清理页面、断开 CDP 或关闭窗口失败时只记告警，包括关闭时的 HTTP 429。已取得的成功、发布结果未知、登录失效或其他主结果和退出码均予以保留。

首版按能力界定兼容范围。客户端须支持 Token 鉴权、按 ID 查询进程与端口、连接现有 Chromium 上下文，以及按 ID 打开和关闭窗口。直接在执行对应操作时校验响应，无最低客户端版本、启动时版本探测或旧接口回退。支持范围不要求“已打开窗口”列表或 `opened` 筛选。例如，存活进程的端口查询返回 HTTP 404 时，报告操作、状态码，并提示检查 Local API 地址和客户端是否支持端口查询。查询超时时，诊断应明确写出哪一步超时。两种情况均在开页前退出 `1` 并保留窗口。

## Testing Decisions

从正式 `sau` CLI 验收，把参数解析、提供方选择、HTTP 客户端、共享托管会话和平台命令放在同一条执行路径上。离线环境模拟比特浏览器 Local API，提供受控的平台页面。断言 CLI 输出、退出码、请求中的窗口 ID、实际提交次数和页面可读写状态。私有方法调用次数和锁文件布局不作为通过条件。可复用 AdsPower 客户端和 CLI 用例里的请求与输出断言，以及现有共享 Profile 的双进程测试。模拟服务使用比特浏览器自己的鉴权和响应样例。[客户端测试](../../tests/test_adspower_client.py) · [CLI 测试](../../tests/test_adspower_cli.py) · [会话测试](../../tests/test_adspower_browser_session.py) · [双进程测试](../../tests/test_shared_adspower_process.py)

### 离线交付标准

| 用例 | 通过条件 |
| --- | --- |
| 20 个正式入口 | 逐项运行 7 个 `check`、7 个 `upload-video` 和 6 个 `upload-note`。核对所选提供方、请求携带的窗口 ID、页面归属、stdout、stderr 和退出码。8 个支持 `--no-publish` 的发布入口读到素材和编辑器就绪、退出 `0`、最终提交零次。其余 5 个发布入口各自在受控页面走完成功路径，最终提交恰好一次，并返回该平台约定的成功结果。 |
| 模式与失败分类 | 覆盖三种凭据的空值、空白、单独激活、每种两两冲突和三者冲突，以及仅设置地址、地址非法、窗口 ID 缺失。`--account` 与 `--folder-id` 不改变目标。断言凭据冲突、非法地址和缺失 ID 均在首个 API 请求前失败，并检查输出已脱敏。分别注入 HTTP 429、HTTP 200 业务失败、连接故障、平台要求登录或验证、派发后结果未知，核对各自的退出码和 stderr 信号。 |
| 两个独立 CLI 进程 | 在冷启动和桌面预开两种初态下验证不同平台可同时编辑、实例一致、同平台占用在开页前失败。两张编辑页各写入不同标记，首条退出后同行仍能追加并读回，桌面原页仍在。断言冷启动打开一次、桌面预开零次、首条退出关闭零次、末条退出关闭一次，核对 ID。覆盖显式与省略显示模式、匹配、冲突及未知。 |
| 中断、重开与清理 | 注入启动回包丢失、连接摘要不一致、进程存活但端口缺失或查询失败、全部 CLI 被强杀、关闭确认延迟及清理阶段的 HTTP 429。检查后继命令何时能加入或重开，未确认时保留现场和草稿，同行与主操作结果独立。对已确认的关闭检查 5 秒及旧进程退出两个重开条件。 |

### 真机通过标准

以下各项在取得对应比特浏览器实测记录后分别标记通过。截至 2026-11-22，用户暂无比特浏览器账号，以下均为**待验证**。实现交付以离线契约通过为准。[验收决定](issues/05-acceptance.md)

1. 为每个平台选一个桌面已登录的窗口，用复制的 ID 执行 `check`。七次各自记录 stdout 仅有 `valid` 且退出 `0`。
2. 选同一已登录 TikTok 和 Instagram 的窗口，同时运行 TikTok `upload-video --no-publish` 与 Instagram `upload-note --no-publish`。两张不同的编辑页各自能读回草稿标记。TikTok 输出发布前检查通过的摘要，Instagram 报告 `prepared`，均退出 `0` 且最终提交零次。
3. 在发布命令占用平台期间再运行同平台 `check`。确认后来者在开页前提示平台占用并退出 `1`，原任务仍可编辑。
4. 从关闭和桌面预开两种初态分别运行并行用例。冷启动总计打开一次，并核对启动回包与端口查询能识别同一浏览器实例。桌面预开总计打开零次。首条退出后确认其页面已清理、关闭请求为零、同行能追加并读回文字。桌面预开场景还须读回桌面原标签的标记。
5. 末条退出时记录对同一 ID 恰好一次的关闭请求，分别记录关闭回包、旧进程退出和原调试端口消失的时刻。再次冷启动前确认至少经过 5 秒且旧进程已退出。

每次记录客户端和 Chromium 内核版本、命令及退出顺序，附脱敏 API 计数、页面标记与最终窗口状态。遇到限流时记录实际 HTTP 状态和业务响应。其余发布入口保留各自的离线结果。

## Out of Scope

窗口创建与批量管理、代理与指纹配置、平台登录及人工验证由使用者在桌面端完成。首版不支持关闭 Token 鉴权的配置。`verify`、`delete`、`article` 和独立素材管理命令沿用各自的现有路径。本次真机验收在最终提交前停止，公开发布作品不属于验收步骤。
