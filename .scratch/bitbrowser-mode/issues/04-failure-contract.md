## Question

冷启动或加入已开窗口时，怎样处理 `--headless` 和 `--headed`？客户端不可达、凭据无效、窗口不存在、CDP 连接失败、HTTP 或业务层限流和停止失败，各应给调用方什么退出码或提示？区分有官方依据的信号与未知响应，延用现有平台登录失效、发布结果未知及清理时保留主结果的约定。

对照[现有退出码](../../../docs/CLI.md#退出码)与[比特浏览器的本机 API 能力](01-local-api.md)。

## Answer

用户决定首版沿用 AdsPower 的行为。

### 窗口启动与加入

| 场景 | CLI 行为 |
| --- | --- |
| 窗口未开 | 显式开关优先，省略时读取 `LOCAL_CHROME_HEADLESS`，缺省为 `False`。无头启动向 `/browser/open` 传窗口 ID、`args=["--headless"]` 和 `ignoreDefaultUrls=true`，省略 `newPageUrl`。有头启动按 ID 普通打开。成功后记录这次请求的模式并继续连接，无需再检查屏幕上是否出现窗口。 |
| 窗口已开，省略开关 | 直接加入当前实例。即使模式未知，或者与本地默认配置不同，也可继续。 |
| 窗口已开，显式传了开关 | 优先用当前实例报告的模式核对。若 API 未报告模式，可采用同一浏览器连接地址对应的共享记录。匹配时加入。冲突或仍未知时，在打开平台页面前退出 `1`，提示窗口模式冲突或无法确认，保留现有窗口。 |

比特浏览器允许窗口预设无头参数，因此普通打开后实际界面可能仍然隐藏。与 AdsPower 一样，冷启动记录的是请求的模式。桌面手动打开的实例可能没有这条记录，不能仅凭窗口 ID 沿用上一次运行的模式。[本机 API 研究笔记](../research/01-local-api.md) · [AdsPower 启动请求](../../../utils/adspower.py) · [共享会话的模式核对](../../../utils/managed_sharing.py)

### 失败时调用方看到什么

| 场景 | 退出码与提示 |
| --- | --- |
| 缺少窗口 ID 或 API 地址格式非法 | `2`，提示修正参数或地址。多种托管凭据同时生效沿用已定的 `1`。[调用方怎样选中比特浏览器并定位已有窗口](02-activation.md) |
| 客户端不可达、Token 被拒绝、指定窗口不存在，或发布前 CDP 连接失败 | `1`，指出失败的操作，并按已知原因提示检查本机服务、Token、窗口 ID 或调试连接。诊断信息隐去凭据。 |
| 探测、查询或启动时收到 HTTP `429` | `11`，由调度方退避。CLI 不因限流自动重试。 |
| HTTP `200` 且 `success=false`，或业务响应无法识别 | `1`，报告操作及可用的脱敏错误信息。仅凭“请求频繁”等业务文案不足以触发 `11`。窗口启动结果未明时，按共享规则保留记录。[冷启动、加入和最后退出时怎样识别同一个窗口](03-shared-window.md) |
| 平台要求登录或人机验证 | `10`。若已经派发发布动作，沿用 stderr 单独一行 `publish_attempted=true`，先核对作品。 |
| 已派发发布动作，随后断线或无法确认发布结果 | `9`，先人工核对作品，禁止自动重发。 |
| 退出时清理页面、断开连接或关闭窗口失败，包括关闭时收到 HTTP `429` | 只告警，保留主操作的结果和退出码。 |

HTTP `429` 是 CLI 对实际响应的分类规则。比特浏览器各版本触发限流时的真实 HTTP 状态和业务响应，仍待真机验收。[现有退出码](../../../docs/CLI.md#退出码) · [哪些证据足以验收比特浏览器托管模式](05-acceptance.md)
