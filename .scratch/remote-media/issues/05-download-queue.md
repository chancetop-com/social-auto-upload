# 入队返回后由谁下载，发布命令怎样接手

Type: grilling
Label: wayfinder:grilling
Status: resolved
Assignee: chancetio (Codex)

## Question

预下载命令在入队后退出，由谁继续消费队列？调度 App 结束等待、确实中断下载，以及消费者意外退出，各自会留下什么可恢复的状态？发布命令收到相同资源目录 ID 和 URL 时，分别考虑仍在排队、正在写入和已中断三种情形。决定何时等待现有下载、何时接手续传，以及多个命令怎样共同遵守下载并发数，避免重复传输或同时写同一个文件。

发布成功清理资源目录时，队列里可能还有写入同一目录的旧下载。怎样避免这些任务在清理后重新创建目录？[发布成功时的清理规则](06-retention.md)

## Comments

- 已确认 CLI 将请求持久化并确保独立的后台下载进程接手后，才返回入队成功。调度 App 随后可以退出，下载继续。队列清空后，后台下载进程自行退出。
- 已确认使用同一 `downloads/` 根目录的所有预下载和发布取材共用一个下载并发上限，跨命令、跨资源目录 ID 生效，默认值为 `1`。
- 已确认发布所需素材优先于仍在排队的普通预下载。正在传输的素材可继续完成。发布需要的素材若已在下载，发布命令等待同一份下载完成。
- 已确认后台下载进程意外退出时，仍在等待素材的命令会立即拉起新的下载进程。没有命令等待时保留队列和断点，下次预下载或发布取材时再恢复。多个命令同时触发恢复时，每份文件只有一个写入者。
- 已确认在等待完成模式下，调度 App 直接终止它启动的预下载 CLI 即可。仅该请求需要的排队项撤下，传输中的素材停下并保留断点；其他命令仍需要的同一份下载继续。入队即返回模式下，原 CLI 返回后，调度 App 退出也不影响后台下载。
- 已确认最终发布可以只使用同一资源目录 ID 下预下载素材的一部分。例如预下载 A、B、C，发布仅传 A、B，此时 C 可能还在排队或下载。

## Answer

入队即返回时，CLI 先将请求持久化，并确保独立的后台下载进程已接手，才报告入队成功。调度 App 随后可以退出。后台进程完成队列中的下载后自行退出。同一 `downloads/` 根目录下，所有预下载与发布取材共用可配置的并发上限，默认同时下载一份素材。

发布命令按资源目录 ID 和完整 URL 查找每份必需素材。已有完整文件时直接使用。素材还在排队时，将原请求提到普通预下载之前，正在传输的文件继续。素材已有写入者时，发布命令等待同一份下载完成。若传输已经中断，则由唯一的写入者检查断点，能续传时接续，否则从头下载。发布所需的素材全部就绪后才交给上传器。

- **调度 App 打断等待。** 在等待完成模式下，直接终止预下载 CLI 即可。撤下仅供这次请求使用的排队项，停止它独占的传输，保留完整文件和断点。其他命令仍需要的下载继续。之后以同一 ID 和原 URL 发布时可以接手。
- **后台进程意外退出。** 仍在等待素材的命令发现后台进程退出，立即拉起新的下载进程。没有命令在等待时，队列和断点保留到下次预下载或发布取材。多个命令同时触发恢复，也只允许一个进程写同一文件。
- **平台确认发布成功。** 即使只发布了 A、B，也要取消同一 ID 下尚在排队或传输的 C。CLI 先让该 ID 的旧请求失效并停止写入，等写入者退出该目录后，再删除整个任务目录。仍在等 C 的命令收到“任务已清理”的结果并结束等待。后台进程重启也不能用旧请求重建目录。清理完成后，调度 App 显式提交的新请求可以使用同一 ID。[哪些本地素材可以清理，由谁触发](06-retention.md)
