# 托管 Profile 默认共享

Status: ready-for-agent

## Problem Statement

同一台 Mac 上，一个 AdsPower Profile 可以同时登录 Instagram 和 TikTok。运营者希望从两个终端分别准备内容，让每条命令到自己的发布时间再提交。现有托管流程按单条命令启动和归还 Profile，调用方需要串行调度。同一个 Profile 即使已经从桌面打开，也缺少让多条 CLI 安全加入、分别退出的约定。

TikTok 如果在丢页后选中了 Instagram 的标签，可能会更改另一份草稿。运营者需要确认每条命令只操作自己的页面，并能从结果中判断该命令是否已经提交。

## Solution

先删除抖音、快手、Bilibili、视频号、大鱼号、百家号、支付宝生活号、微博、虎扑、雪球和知乎的平台支持。完成移除后，第一批为 Instagram、TikTok、大陆版小红书和 Rednote，第二批为 Facebook 个人、Facebook Page 和 YouTube。[前置工单 #20](issues/20-remove-platforms.md)

同机、同一操作系统用户的兼容 CLI 默认共享 AdsPower 或 Multilogin X（MLX）的同一 Profile。用户沿用现有托管命令和 Profile 参数，无需传入 `--share-profile`。不同平台可以并行，包括一个平台等待 `--not-before` 时运行另一个平台的 `check` 或发布。同一平台同时限一条托管命令，后来者立即收到带平台名的占用提示和退出码 `1`。

每条命令在现有 Profile 上下文中新开页面，独立等待、提交并报告结果。第一条命令离开后，同行仍能编辑自己的草稿。**最后一条已加入的托管命令离开时关闭整个 Profile，包括用户从桌面打开的原标签页。** 这一约定适用于冷启动、手动打开和崩溃后重新加入的 Profile。

## User Stories

1. 作为运营者，我希望沿用平时的 AdsPower 或 MLX 命令，以便直接使用 Profile 中已登录的账号。
2. 作为运营者，我希望同时从两个终端启动 Instagram 和 TikTok，以便两份内容都能在预定时刻前准备好。
3. 作为运营者，我希望 CLI 能加入我从桌面打开的 Profile，并另开标签页，以便在命令执行期间保留我原先浏览的位置。
4. 作为调度方，我希望同一 Profile 上的同平台检查与发布共享一个名额，以便在第二条命令打开页面前就能识别冲突。
5. 作为调度方，我希望一条小红书命令等待发布时间时，TikTok 仍能加入，以便各平台独立履行自己的发布时间约定。
6. 作为多账号运营者，我希望不同 Profile 能同时执行同一平台的命令，以便分别操作两个账号。
7. 作为运营者，我希望 Facebook 个人和 Facebook Page 能并行，大陆版小红书和 Rednote 也能并行，以便按各自的发布目标安排任务。
8. 作为调度方，我希望从不同目录、安装位置或虚拟环境启动的 CLI 都能识别同一 Profile 的占用，以便多个调用方可以共同调度。
9. 作为运营者，我希望每条命令只操作自己的编辑器、探针和弹窗，以便一条命令超时、失败或先完成时，同行仍能继续编辑原稿。
10. 作为 CLI 用户，我希望帮助、示例和安装后的命令列出同一组受支持平台，调用已移除的平台时能立即得到用法错误。
11. 作为运营者，我希望启动 Profile 的命令可以先离开，以便后加入的任务仍能按原定时间完成。
12. 作为运营者，我希望最后一条命令离开时归还整个 Profile，以便从桌面或 CLI 启动时都能预期浏览器何时关闭。
13. 作为调度方，我希望新命令在上一次停止仍在进行时有界等待，以便明确得知何时可以使用 Profile，何时需要处理故障。
14. 作为运营者，我希望进程被强杀后能在当前 Profile 上开始新任务，以便恢复工作，并保留旧草稿供核对。
15. 作为调度方，我希望按每条命令的结果文件、退出码和提交信号决定是否重跑，以便同行的失败或清理告警不会导致重复发布。
16. 作为本机用户，我希望只有当前操作系统用户能读取共享连接记录，以便其他用户无法从记录或日志中取得访问凭据。

## Implementation Decisions

### 平台移除

先移除这 11 个平台的全部本地及托管 CLI 动作、专属上传器、脚本、示例与仅供这些平台使用的依赖，并更新支持清单和测试。Bilibili 的本地 biliup 流程也在移除范围内。保留通用本地文章工具 `sau article` 及其渲染依赖。已有账号文件、浏览器 Profile、素材和历史发布结果由用户保管。

### 加入与离开

- 由托管会话层统一协调。CLI 提供平台身份，Managed browser provider 提供指定 Profile 的状态、当前连接及 Start、Stop 操作；上传器通过 `BrowserSession` 使用现有上下文。平台使用资格覆盖整条命令，从启动、登录探测到编辑、等待和清理。同一条命令内部的探针结束不能提前归还 Profile。
- 使用本机进程锁。锁的身份由同一操作系统用户、provider 和 Profile ID 确定。MLX 的 folder 与 AdsPower 的服务地址用于核对资源。改变地址拼法、folder、凭据或账号别名不能为同一资源取得第二组锁。资源无法确认、无法可靠加锁或无法安全读取记录时，在接管浏览器前报错退出。
- 同一 Profile 按 CLI 平台判定占用。`facebook` 和 `facebook-page` 可以并行，两条 `facebook-page` 即使指定不同主页也互斥。大陆版小红书和 Rednote 分开计数。已占用的平台立即拒绝后来者，包括两次 `check`、检查与发布的任一到达顺序，以及两次发布。
- 串行协调首次启动、加入登记和最后归还。不同平台同时申请空闲 Profile 时，合计只发一次 Start。Profile 已打开时，确认当前连接属于指定 Profile，且与新命令明确要求的启动设置兼容，再加入。设置冲突时，在开页前拒绝新命令，已有命令继续执行。
- 仍有同行使用时，离开者只清理自己的页面、断开自己的连接并释放资格。最后离开者发一次 Stop，桌面标签也随 Profile 关闭。加入失败的命令没有归还责任。若申请的平台已空闲而旧会话正在停止，新命令有界等待；确认停止完成后重新申请，超时或结果仍未知时报告原因并退出。
- 兼容 CLI 在项目支持的桌面环境及 Python 3.10–3.12 间遵守同一套锁和记录规则。各进程使用自己的环境凭据。会话目录和连接记录限当前用户访问，共享记录不保存 token 或 API key，日志不输出凭据或 CDP 连接地址。

### 页面、内容与发布结果

- 每条命令新开主页面，跟踪自己的登录探针、预览、编辑器及结果核对页。由自己的页面直接打开、可追溯到该页面的弹窗归当前命令。导航、输入、结果监听和清理均以此为界。标签顺序、焦点、URL 相同和出现时间都不足以确认归属。
- TikTok 提交前丢失自己的页面时，本次报错退出，同行可以继续编辑。提交后丢页按该动作已有的结果语义处理，不再点击发布。
- 各命令独立处理客户端发布闸门、提交次数、结果文件和退出码。沿用各动作已有的成功、提交前失败、发布结果未知、登录失效及人机验证契约，包括适用时的 `publish_attempted=true`。Instagram 和 Facebook Page 默认各用带 UUID 的结果文件。显式传入 `--result` 时由调用方分配不同路径；若指向同一文件，两条命令照常执行，后写入者覆盖前一份。

### 中断与恢复

| 观察到的状态 | 命令行为 |
| --- | --- |
| 一条命令被强杀，仍有同行持锁 | 被终止进程的平台资格随进程释放。同行继续使用原页。该平台的新命令取得资格后另开页面，旧草稿留在原页。 |
| 全部 CLI 被强杀，Profile 仍开着，或用户已将它关闭后手动重开 | 允许 Profile 保持打开。下一条命令核对当前连接、另开页面，最后离开时按正常规则关闭整个 Profile。 |
| Start 响应丢失或不足以判断启动结果 | 保留浏览器。后继命令重新查询；已打开且可连接则加入，确认启动已结束且空闲才可 Start。仍在启动、状态未知或当前连接不可用时报错退出，避免重复 Start 或补偿 Stop。 |
| 最后离开时 Stop 失败 | 告警并保留主操作结果及退出码。若 Stop 可能仍在执行，后来者有界等待；确认操作结束后按当前活动或空闲状态处理。 |
| 进程退出前可能已经点击发布 | 已落盘结果保留。强杀可能来不及产生结果或退出码。恢复不补写结果、不续点旧草稿；调用方先到平台核对作品，再决定是否重跑。 |

## Testing Decisions

主要验收入口是用户实际运行的 `sau <platform> check|upload-*`。从 CLI 观察退出码、诊断、结果文件和提交次数，从 provider 观察 Start、Stop 和最终 Profile 状态，从浏览器观察每个编辑器实际收到的内容。通过这些外部行为验收，避免测试绑定锁文件名称、内部计数或辅助函数的调用顺序。沿用现有 CLI 分派、两家 provider 的模拟 HTTP 与 BrowserSession 测试、平台上传及本地模式回归用例。

**先验收平台移除。** 检查安装后的 `sau --help` 和平台解析。11 个旧平台名均作为未知子命令以 `2` 退出，解析失败时不访问 provider、浏览器或账号文件。逐一确认保留的平台与本地文章工具仍可调用。[移除清单及验收条件](issues/20-remove-platforms.md)

**离线逐入口验收。** 保留的 7 个平台共 20 个托管入口，包括 7 个登录检查、7 个视频发布和 6 个图文发布。每个入口预置一份同行草稿，核对当前命令的页面、清理、结果及退出码，并验证同行仍能在原位置编辑。发布测试覆盖提交前失败、已提交、结果未知和登录失效。

| 批次 | 平台 | 每个平台的托管动作 | 入口数 |
| --- | --- | --- | --- |
| 第一批 | Instagram、TikTok、大陆版小红书、Rednote | `check`、`upload-video`、`upload-note` | 12 |
| 第二批 | Facebook 个人、Facebook Page | `check`、`upload-video`、`upload-note` | 6 |
| 第二批 | YouTube | `check`、`upload-video` | 2 |

**在 macOS 上用两个独立 CLI 进程验证生命周期。** 从不同工作目录和 Python 虚拟环境启动正式入口，复用可控的 provider 响应，以同步点重现并发顺序。现有双进程示例提供了模拟 provider 下的锁和退出顺序先例。

- 不同平台同时冷启动只发一次 Start。启动者先退出时 Stop 为零，同行仍能编辑；最后一条退出后总计一次 Stop。显式启动参数冲突和连接不可用时，核对拒绝发生在开页前，同行继续工作。
- 同平台覆盖检查与检查、检查与发布的两种到达顺序、发布与发布，同时申请时只有一条成功取得资格。用可控时间让小红书真正进入 `--not-before` 等待，此时 TikTok 可加入，第二条小红书立即以 `1` 退出。该测试使用发布等待路径，`--no-publish` 会跳过等待。
- 验证不同 Profile 独立运行、Facebook 个人与 Page 并行、两条不同目标主页的 Page 命令互斥，以及大陆版小红书与 Rednote 并行。Facebook 用离线编辑器在等待前后分别观察个人发帖主体、Page 名称和可见主页标识。
- 覆盖正常退出、单进程和全部进程被强杀、桌面重开、Start 响应丢失和新命令在 Stop 期间到达。分别断言释放了哪个平台、能否取得当前连接、超时诊断、Start/Stop 次数、原有结果和可观察到的提交次数。注入 Stop 失败时，断言主操作的结果与退出码优先。
- 检查会话目录和记录的实际所有者与权限，检查日志及记录中的敏感字段。用本地模式回归验证原有入口、Profile 生命周期、结果格式及退出码。

**用本机 Chromium 的两个独立连接验证页面与内容。** 让 Instagram 和 TikTok 编辑带不同标记的草稿。在两页 URL 相同或标签顺序改变时关闭 TikTok 的编辑页，核对这条命令的结果、实际提交次数，以及 Instagram 草稿的内容、位置和可编辑性。

**在现有 Mac 上用 AdsPower 验收 Instagram 与 TikTok。** 使用同时登录两者的测试 Profile，让两个编辑阶段实际重叠并留下可辨认的不同内容。真实发布动作一律用 `--no-publish` 停在最终提交前。

| 真机场景 | 通过条件 |
| --- | --- |
| 同时申请空闲 Profile | 合计一次 Start。两条命令各用自己的新页；启动者先离开，同行仍可编辑，最后一次 Stop 后 Profile 已关闭。 |
| 桌面先打开并留有带标记的原标签 | 两条命令直接加入。首条离开后，原标签和同行草稿均可用。最后一条离开时一次 Stop 关闭整个 Profile。 |
| 强杀全部 CLI 后再运行 | 分别保留浏览器、手动关闭后重开。两次都能从当前连接新开页面，最后一次 Stop 关闭 Profile。已落盘结果保留，旧草稿没有触发提交。 |

每次记录 macOS 和 AdsPower 版本、命令进入与离开顺序、脱敏的 Start/Stop 次数、页面内容标记和最终 Profile 状态。大陆版小红书使用另一测试 Profile，小红书等待时 TikTok 加入的组合在离线环境验证。MLX 本轮用模拟 Launcher 验证同一契约；取得账号后补桌面实测。Windows 和 Linux 的双进程与权限验收待有环境后分别记录。

## Out of Scope

- 共享会话只适用于保留平台的托管检查与发布。本地浏览器 Profile 和纯本地工具沿用原有行为。
- 跨机器或跨操作系统用户协调。与旧版 CLI、独立工具混用时由调用方串行。
- 判断浏览器最初由谁启动、给浏览器实例增加归属标记，以及在所有 CLI 被强杀后另设常驻进程清理浏览器。
- 把多个平台的发布合并成一个批次、联动取消或回滚，以及为显式相同的结果路径增加冲突检测。

## Further Notes

实施与验收以本规格的共享规则为准；既有 AdsPower 和 MLX 规格中由调用方串行同一 Profile、由启动者停止 Profile 的规则已被取代。若桌面实测显示产品版本间有差异，再根据实际观察决定兼容处理。[托管 Profile 默认共享决策地图](map.md)

2026-11-18，在 macOS 26.6.2 上从提交 `3936aae` 的三个干净副本执行全量离线测试。平台发布组通过 49 项，双进程及恢复组通过 53 项，既有回归通过 1,447 项，合计 **1,549 项通过**，另有 792 个子用例通过。5 项 Windows 权限用例与 2 项按需开启的真实服务 smoke 在本次离线运行中跳过。
