## Question

哪些场景用双进程测试、真实浏览器双连接、各平台动作测试及两家桌面应用的测试 Profile 分别覆盖？如何验证从空闲启动的共享会话只需一次 Start 和 Stop、先退出者不影响同伴、各平台页面和内容互不干扰，以及本地模式和发布结果契约兼容？真实验证应如何在最终发表前停止？

用户手动打开 Profile 并留有原标签页时，怎样在两家 provider 上验证两条不同平台的命令直接加入、各开新页？第一条离开后，原标签页和同伴的页面应仍可用；最后一条离开后应只发出一次 Stop，整个 Profile 关闭。若全部命令被强杀，怎样分别验证下一条命令能加入遗留的或用户手动重开的 Profile，并在最后离开时关闭？已有发布结果应独立保留。Start 响应丢失、Stop 结果未知和当前连接不可用时，应观察哪些证据？[进程中断后怎样识别和恢复遗留会话](04-abandoned-session.md)

在同一 Profile 上，怎样验证小红书等待发布期间 TikTok 可以加入，而后来的小红书命令在打开页面前立即报告占用并退出？验证应覆盖同平台 `check` 与 `check`、`check` 与发布（两种到达顺序）、发布与发布，以及两条命令同时到达时只有一条取得使用资格。

怎样在不同工作目录和 Python 虚拟环境中验证两条命令使用同一组锁？同一 Profile 上应验证 `facebook` 与 `facebook-page` 可以并行，大陆版小红书与 Rednote 也可以并行。已有 `facebook-page` 命令运行时，第二条 `facebook-page` 命令即使指定不同主页，也应立即报告占用并以 `1` 退出。各受支持桌面环境还需要什么证据，才能确认锁在进程退出时释放，且 CLI 保存的连接地址仅当前用户可读？

Facebook 个人与 Facebook Page 并行时，用什么证据分别确认两个编辑器在等待前后仍指向预期发布目标？逐入口及剪贴板交错场景见[每个托管动作怎样只操作自己的页面和内容](03-command-isolation.md)。

## Answer

以下是实施完成后的通过条件。本次确定验收口径，实测结果待实施时填写。

### 在现有 Mac 上用 AdsPower 验证共享

用已登录 Instagram、TikTok 和 Rednote 的 Profile，独立启动 Instagram 和 TikTok 两条 CLI。让两条命令的编辑阶段确实重叠，在自己的页面放入不同的可辨认内容。真实发布入口使用 `--no-publish` 停在最终提交前。另一个 Profile 只登录了大陆版小红书，保留现有账号安排。

| 场景 | 通过条件 |
| --- | --- |
| Profile 空闲，两条命令同时到达 | 合计一次 Start。两条命令用同一个 Profile，各自打开新页。启动者先退出时 Stop 次数为零，同伴仍能编辑原草稿。最后离开时合计一次 Stop，桌面或状态接口可观察到 Profile 已关闭。 |
| 桌面已打开 Profile，并留有带标记的原标签页 | 两条命令直接加入，均另开自己的页面。第一条离开后原标签与同伴草稿都还在。最后一条离开时一次 Stop 关闭整个 Profile。 |
| 两条 CLI 均被强制终止 | 分两次验证：一次保留仍在运行的浏览器，另一次由用户关闭后手动重开同一 Profile。新命令均须通过当前连接另开新页，最后离开时一次 Stop。已落盘的结果保持原样，旧草稿不会触发新的提交。 |

每次记录系统及 AdsPower 版本、两条命令进入和离开的顺序、脱敏的 Start/Stop 次数、可辨认的页面内容和最终 Profile 状态。Multilogin X 本轮用模拟 Launcher 验证相同契约，待取得账号再补桌面实测。

### 用两个独立 CLI 进程验证互斥与故障恢复

在 macOS 上从不同工作目录和 Python 虚拟环境运行正常 CLI 入口，以可控制状态和响应的模拟 provider 记录调用。用同步点制造同时申请、等待和停止中的交错，让测试能稳定重现这些顺序。

- **平台占用。** 同一 Profile、同一平台逐项覆盖两次 `check`、`check` 与发布的两种先后顺序，以及两次发布。同时申请只有一条获准，另一条在开页前立即报告平台名并以 `1` 退出。小红书进入 `--not-before` 等待期间，TikTok 可加入，第二条小红书立即退出。在离线测试中控制等待和放行，现有 `--no-publish` 会跳过等待。[CLI 等待语义](../../../docs/CLI.md)
- **平台及 Profile 的区分。** Facebook 个人与 Page、大陆版小红书与 Rednote 分别可在同一 Profile 并行；两条 Page 命令即使指定不同主页仍互斥。不同 Profile 可独立运行。一方失败或被强杀后，该平台的锁释放，同行照常完成，仍被同行占用的平台继续拒绝后来者。
- **启动与停止结果不明。** 注入 Start 响应丢失，核对后继命令重新查询状态；可连接时加入、确认空闲时才重新启动，状态不明或当前连接不可用时报告原因并退出。核对无重复 Start、无补偿 Stop。让新命令在旧会话 Stop 期间到达，核对它有界等待；结果仍未知时退出。Stop 失败只告警，保留离开者已有的主操作结果。[进程中断后怎样识别和恢复遗留会话](04-abandoned-session.md)
- **系统与权限。** 正常退出和强制结束进程后都验证另一进程可立即取得已释放的资格。在 Mac 检查会话目录、记录的所有者与实际访问权限，确认仅当前用户可读取连接记录；检查共享记录不含 token 或 API key，日志不泄露凭据或连接地址。Windows 和未来可能使用的 Linux 待有相应环境后复跑双进程与权限用例，按系统分别记录。Linux 托管桌面部署若成为需求，再核对实际 provider 环境。[项目现有部署前提](../../../docs/CLI.md#mlx-部署前提)

### 用离线平台测试与真实 Chromium 双连接验证动作

按既定清单，通过各自 CLI 入口覆盖 17 个 `check`、16 个视频、8 个图文和 3 个文章动作。每例核对自己打开、导航和关闭的页面，自己的退出码或结果，以及同行草稿仍能继续编辑。本地模式沿用现有回归用例，核对进入本地 Profile 流程并保留原退出码与结果格式。[逐入口清单与预期](03-command-isolation.md#逐入口验证)

用真实 Chromium 的两个独立连接和本机可控页面复现 TikTok 丢页、微博等待弹窗时同行开页、两个文章编辑器交错粘贴不同正文与图片。分别回读编辑器实际内容，覆盖错贴和平台正常改写。Facebook 个人和 Page 用离线编辑器分别观察等待前后的发帖主体与目标主页。已提交、提交后状态未知、登录失效等结果分支在离线测试触发，核对各命令的结果文件、退出码、适用时的 `publish_attempted` 和提交次数。并发用不同结果路径；调用方显式指定同一路径时的约定见[两条命令指定同一结果文件时由谁处理冲突](07-result-path-collision.md)。
