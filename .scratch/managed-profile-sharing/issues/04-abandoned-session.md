# 进程中断后怎样识别和恢复遗留会话

Label: wayfinder:grilling
Type: grilling
Status: resolved
Assignee: LukeChen
Blocked by: 01, 02

## Question

启动者被终止、只有最后一个使用者崩溃、Start 响应丢失、Stop 失败或用户手动重开同名 Profile 后，下次 CLI 应根据什么证据继续、提示占用或请用户处理？怎样保留其他任务的运行状态及已点击发布的原有结果，避免误关浏览器或重复发布？

## Comments

2026-11-18，用户确认，最后一条 CLI 退出后，若已无人持锁而 Profile 仍开着，下一条 CLI 可以直接新开标签页使用。用户随后明确：「手动打开的 profile 也可以直接开新 tab 用，用完只关 CLI 自己开的 tab，profile 留着」。

用户补充，若所有 CLI 崩溃后仍能确认浏览器是上一次 CLI 打开且一直运行到现在的，允许新命令接管，用完后由最后一个 CLI 关闭。同机共用的是同一个已打开的浏览器。只有中途关闭后重开，才需要重新判断这次是谁打开的。

随后在一个 macOS AdsPower 版本实测了当时讨论的接管条件。启动时传入一次性参数，新进程可核对并通过同一条浏览器连接关闭。桌面重开或先打开时，相应 CLI 标记均未出现在浏览器参数中。[实机调查记录](../research/06-crash-ownership.md)

用户最终选择「没人在就关掉，不管谁开的」。上面的启动者识别方案留作讨论记录。

## Answer

同机同一用户的托管 CLI 以仍在使用该 Profile 的命令数决定何时关闭。最后一个使用者离开时关闭整个 Profile，手动打开的标签页也会一并关闭。[谁负责加入、离开和停止共享托管会话](02-process-lifecycle.md)

- **仍有命令运行。** Instagram 命令退出后，它持有的平台锁随进程释放。TikTok 继续在自己的页面按原定时间发布。新的 Instagram 命令取得平台锁后另开标签页，旧草稿留在原页。仍有人持锁的平台按既有规则报告占用。[谁负责加入、离开和停止共享托管会话](02-process-lifecycle.md) · [每个托管动作怎样只操作自己的页面和内容](03-command-isolation.md)
- **无人持锁，Profile 仍开着。** 所有 CLI 同时被强杀时，没有进程能当场执行 Stop。下一条命令取得本平台的锁后，使用指定 Profile 的当前连接，新开自己的标签页，用完按同一规则离开。桌面手动打开、手动重开和 CLI 崩溃留下的 Profile 都走这一流程。
- **启动结果未知。** Start 响应丢失时保留浏览器。后续命令重新查询指定 Profile 的实际状态。若已打开且能取得当前连接，可以加入。若能确认启动已结束、Profile 空闲，按正常流程启动。仍在启动、状态不明或无法取得当前连接时，报告原因并退出，避免重复 Start 或补偿 Stop。两家产品的连接和关闭行为见[哪些证据足以验收托管 Profile 默认共享](05-acceptance.md)。
- **停止失败。** 成功加入的最后一条命令离开时尝试 Stop。失败只告警，保留本条命令的主操作结果。若 Stop 可能仍在执行，后来者按既定规则有界等待，超时或结果仍未知就退出。确认停止操作已结束后，再按当时看到的活动或空闲状态处理。[CLI 退出码](../../../docs/CLI.md#退出码)
- **发布是否已提交。** 恢复会话只为新命令提供页面。其他任务继续各自产生结果，已有发布结果保持原样。被强杀的命令可能来不及写结果或报告退出码。若无法排除已经点击发布，由调用方先核对平台作品，再决定是否重跑。恢复流程不续点旧草稿，也不替上一条命令补写结果。[发布结果与重试规则](../../../docs/CLI.md#退出码)
